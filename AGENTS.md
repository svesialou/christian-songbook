# AGENTS (christian-songbook)

## Purpose
Проект: 
- **Название:** Christian Songbook Web
- **Формат:** локально-first веб-приложение (PWA) для сбора и просмотра песен с аккордами.
- **Стадия:** проектный контур и план, код еще не привязываем к GitHub.

## Базовые принципы
1. **Надежность данных выше скорости разработки.**
2. **Ни одной новой зависимости без причины и оценки поддержки.**
3. **Минимум абстракций, максимум понятности.**
4. **Офлайн-работа должна быть валидной из первого релиза MVP.**
5. **Нет кода, зависящего от внешней доступности сети для базовой навигации и чтения уже загруженного контента.**

## Технологический стек (рекомендуемый)
- React + TypeScript + Vite
- PWA через `vite-plugin-pwa`
- Хранение данных: `IndexedDB` через `idb` + fallback на `localStorage`
- Backend foundation: Go API + MySQL, Docker-first, read-only catalog API уже относится к фазе 1.5
- Стили: CSS-модули или Tailwind (по решению команды)
- Хранилище состояния: Redux Toolkit или Zustand (не использовать лишний глобальный state)

## Рабочие правила для этого проекта
- Главная зона ответственности — `README.md`, `docs/requirements.md`, `docs/architecture.md`, `docs/roadmap.md`, `docs/tasks/*`.
- Любое изменение, влияющее на пользовательскую модель песни/данные, должно пройти ревью через `docs/requirements.md` и `docs/architecture.md`.
- Любые функции live/синхронизации относятся к фазе 2/3, и не делаются в фазе 1.
- Не начинать новый публичный backend API, admin mutation API, auth/security flow, MySQL schema change или migration без отдельного подтверждения. Текущий read-only catalog API остается в границах phase 1.5.
- Backend/MySQL планировать в фазе 1.5 как источник истины для каталога и будущих пользовательских связей.
- После каждого цикла разработки выполнять quality gate из `docs/development-quality-gates.md`.
- Перед финальным ответом выполнять self-review по `docs/self-review-prompt.md` и не заявлять проверки, которые фактически не выполнялись.
- Для всех frontend-изменений соблюдать `docs/frontend-guardrails.md` и `docs/ui-ux-design-system.md`.

## Рекомендуемый порядок разработки
1. `requirements -> architecture -> phase-1 tasks`
2. Реализовать фазы последовательно по DoD.
3. После каждого цикла проверить frontend/API/runtime по quality gate.
4. После каждой фазы обновлять roadmap и список риска.

## Ограничения и риски, которые учитывать с старта
- Правообладание на тексты и аккорды: без явного источника/лицензии публикация запрещена.
- Не смешивать «локальную модель для офлайна» и «данные сервера» без политики конфликта.
- Backend не должен делать базовое чтение каталога network-only.
- Избегать привязки к старому React Native API из оценочного репозитория.

## Что считается готовым в рамках этапов
- Фаза считается завершенной, если выполнены критерии DoD в `docs/roadmap.md` и все задачи фазы отмечены в `docs/tasks/phase-*.md`.
- Изменение считается готовым только после self-review, проверки затронутых frontend/backend/API частей и честного отчета о командах/ручных проверках.

## Команды для проверки документации
- Перед началом реализации проверить, что все новые файлы описаны в `docs/roadmap.md`.
- После добавления фазы/изменения правил обновить `docs/requirements.md` и `docs/architecture.md`.
