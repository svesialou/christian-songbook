# Требования проекта Christian Songbook

## Бизнес-требования
1. Быстрый сборник песен для церкви (чтение + разметка текста + аккорды).
2. Автономная работа без интернета на уже загруженном каталоге.
3. Доступность на телефоне и десктопе.
4. Гибкость под будущий live-режим (разные view для разных людей).
5. Единый источник каталога и будущих пользовательских связей через backend + MySQL.

## MVP (Фаза 1) — должны быть обязательно
- Единая база песен, поставляемая вместе с приложением и доступная обычному пользователю без ручного импорта.
- Импорт/экспорт JSON допускается только как admin-инструмент, не как пользовательский сценарий.
- Карточка песни:
  - текст,
  - аккорды,
  - отображение/скрытие аккордов,
  - смена тональности,
  - переключатель повтора припева.
- Поиск по названию и тексту.
- Сборники и недавние песни.
- Тема и размер текста (минимум базовый + увеличенный).
- PWA установка + offline-кэш приложения и данных.
- Работа со списком без сети на уже сохраненных песнях.
- Для обычного пользователя не должно быть кнопок импорта/экспорта или выбора источника базы.

## Фаза 1.5 — Backend + MySQL foundation
- Backend работает параллельно с PWA и не ломает offline-first чтение.
- MySQL становится источником истины для каталога песен и будущих пользовательских связей.
- Frontend получает каталог как опубликованный snapshot и сохраняет его локально.
- Admin import/export/редактирование каталога переносится в backend/admin-сценарий.
- Обычный пользователь не зависит от backend для открытия уже загруженных песен.
- Новые schema/API/migrations поверх текущего read-only catalog foundation не реализуются без отдельного подтверждения.

## Нефункциональные требования
- Accessibility: контраст, читабельный минимум 16px, фокус/акцентные состояния.
- Производительность: список песен с быстрым скроллом, без «задержек на вводе».
- Безопасность: в приложении не хранить чувствительные данные.
- Локализация: русский UI по умолчанию, расширение на другие языки возможно.
- Backend SQL: только параметризованные запросы, явные индексы, миграции с rollback notes.
- Docker-first запуск backend + MySQL для локальной разработки.
- После каждого development cycle обязательна проверка frontend на нескольких разрешениях, API-интеграции и offline/PWA поведения, если эти зоны были затронуты.
- Статусы источника каталога, сети и sync должны быть видимыми пользователю и не должны кодироваться только цветом.

## Требования 2 фазы
- Пользовательские связи и setlists должны опираться на backend/MySQL foundation.
- Режимы ролей:
  - Lead, Singer, Chords-only/No-chords.
- Поддержка пресетов показа для каждого участника.
- Базовая локальная модель текущего места песни (`songId`, `sectionId`, `lineIndex`) как foundation для будущей синхронизации.
- Локальный автопереход строк по `bpm`, `beatsPerLine` и `introBeats`, чтобы музыкант мог начать со вступления и не пропустить первую строку.

## Требования 3 фазы
- Live-сессии используют backend как контрольный слой состояния, но PWA не теряет офлайн-режим чтения.
- Live синхронизация между устройствами (источник источника прогресса через мастер-устройство).
- Режим «проектора» и «рабочего экрана».
- Экспорт/импорт «сессии» (set-list + пресеты).

## Не входит в текущий этап
- Авторизация и роли через соцсети/внешние identity-платформы.
- Реализация нового публичного backend API, admin mutation API и новых MySQL schema changes без отдельного подтверждения.
- Финансовые/монетизационные механики.
- Собственный audio-проигрыватель и редактор нот.

## Критические риски
- Правовой аспект контента.
- Несогласованность источника одной и той же песни между MySQL, PWA snapshot и локальным кэшем.
- Плавающая точность синхронизации и UX в live.
- Миграции MySQL и admin-доступ требуют отдельной security-проработки.
