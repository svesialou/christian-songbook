# Roadmap

## Фаза 1 — MVP web-сборник (4–6 недель)
### Цель
Собрать устойчивый офлайн-first сборник с аккордами, единой встроенной базой и удобным чтением.

### Ключевые вехи
- Подготовка скелета проекта (Vite + React + TS + PWA).
- Единый встроенный каталог песен без пользовательского импорта/экспорта.
- Список + поиск + карточка песни.
- Аккорды: показать/скрыть, транспонирование, повтор припева.
- Сборники и недавние песни.
- Настройка шрифта и базовая тема.

### Definition of Done (DoD)
- После установки приложение работает без интернета на уже загруженном каталоге.
- Поиск и открытие любой песни выполняется без ошибок.
- Переключение аккордов и транспонирование влияет только на отображение.
- Есть понятная модель единой встроенной базы и отдельный admin-only путь управления каталогом.
- Для обычного пользователя нет import/export UI.
- Frontend вручную проверен на mobile/tablet/desktop разрешениях по `docs/development-quality-gates.md`.
- Self-review выполнен по `docs/self-review-prompt.md`, а финальный отчет содержит только подтвержденные проверки.

### Риск/отложение
- Если не собрался офлайн-поток, фаза не закрывается.

## Фаза 1.5 — Backend + MySQL foundation (3–5 недель, параллельно с hardening MVP)
### Цель
Подготовить backend и MySQL как источник истины для каталога, admin-управления и будущих пользовательских связей, не ломая offline-first PWA.

### Ключевые вехи
- Подтвердить backend stack: Go API + MySQL по умолчанию.
- Docker-first локальный запуск backend + MySQL параллельно с PWA.
- Draft MySQL schema для песен, секций, строк, аккордов, версий каталога.
- Read-only catalog API: версия каталога, список песен, детальная песня.
- Admin-only flow для заявок, добавления, редактирования и публикации каталога.
- PWA snapshot sync: backend -> локальное хранилище -> офлайн-чтение.
- Предварительная модель пользователей: collections/setlists, roles, live sessions.

### DoD
- Есть утверждённый backend/MySQL план и migration draft.
- Есть стратегия индексов и основных access patterns.
- PWA не зависит от backend для чтения уже загруженного каталога.
- Admin mutation API закрыт `ADMIN_API_KEY`; полноценные users/roles/audit остаются hardening-задачей перед broader team administration.
- Full-stack проверка подтверждает, что frontend получает catalog snapshot из backend и сохраняет offline fallback.

### Риск/отложение
- Не внедрять schema/API в код без отдельного подтверждения.
- Не переносить пользовательский read-flow на network-only модель.

## Фаза 2 — Live foundation (3–5 недель)
### Цель
Подготовить архитектуру для разных экранов ролей, пользовательских связей и синхронизации в будущем.

### Текущий статус
- Локальный foundation начат: `Lead`, `Singer`, `Chords` доступны как view presets на устройстве без server-side users/live sync.

### Ключевые вехи
- Режим пресетов отображения (Lead / Singer / Chords-only).
- Модель плана набора песен (`setlist`) поверх backend/MySQL foundation.
- Связи пользователей со сборниками, setlists и ролями.
- Блоки «что сейчас поётся» для будущей передачи состояния.
- Экран для управления (master) и экран воспроизведения.
- Draft событий будущей синхронизации: `docs/live-sync-events.md`.

### DoD
- Можно переключать пресеты без потери производительности.
- Не сломан MVP flow, новые сущности не меняют офлайн поведение.

### Риск/отложение
- Не добавлять полноценную сеть/сокеты до решения протокола и роли мастера.

## Фаза 3 — live sync (4–6 недель)
### Цель
Добавить синхронизацию между устройствами и гибкие сценарии презентации.

### Ключевые вехи
- Канал синхронизации (WebSocket/RTC/long-poll fallback).
- Отметка текущего куплета/строки/слова.
- Автоматическая прокрутка и подсветка.
- Режимы экранов (владельцы пульта, музыканты, вокалисты).

### DoD
- Несколько устройств в одной сессии показывают согласованное положение слова/аккорда.
- Нет деградации офлайна после выхода из режима sync.
